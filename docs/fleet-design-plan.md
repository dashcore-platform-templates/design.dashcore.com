# One look for the fleet — the plan

**Decided 16 October 2026.** design.dashcore.com absorbs `dashcore/ui`. Every internal Dashcore app takes one style. The package that carries it is `dashcore/design-kit`.

This settles the question `PURPOSE.md` left open: which of the two documents governs the fleet's own apps. The answer is this repository's `standard/`. `dashcore/ui` and its `DESIGN.md` are retired once nothing requires them.

Two catalogue names differ from their repositories: delivery is `dashcoretech/dcos.dashcore.com`, and website is `dashcoretech/dashcore.com` (not the `website.dashcore.com` folder).

No app requires `design-kit`. Only finance and login use Flux, and both are on `dashcore/ui` too. This app uses Flux and is the 25th, audited against its own standard already.

**Two standards, and they disagree.**

| | `dashcore/ui` (`DESIGN.md`) | This repository (`standard/`) |
|---|---|---|
| Type | Fraunces and Inter | One of five pairings. Fraunces and Inter is not one of them. |
| Accent | `#4a4438`, a near-ink olive | A hex at saturation 45–85. `#4a4438` fails that rule. |
| Neutrals | Its own warm set (`#f5f2ec` page) | Tailwind's stone for `warm` |
| Radius | 4px ceiling, enforced by a clamp | `sharp`, `soft` or `round` |
| Components | Blade, works without Flux | Mapped to Flux |
| Tokens | `dc-*` | Role names: surface, sunken, strong/default/muted |

**Two ways of delivering a design, and only one of them updates.**

- `dashcore/ui` is imported from `vendor/`. A release reaches every app on `composer update`. That is the property we want.
- `design-kit`'s `design:apply` writes the tokens into the app's own `app.css` (`Applier::applyCss`). It's a copy, so a change here reaches nobody until somebody re-applies it in each repo.

## The shape we're building

### 1. A style is a built-in, named preset

A **style** is the seven decisions, a name, and a version. It ships inside design-kit.

- **`dashcore`** is the internal style. Every internal app uses it, and no internal app chooses its own.
- **Client designs** keep working as they do now: rows here, exported as a pack. They're styles that live in the database rather than in the package.

An internal app's `design/design.json` holds only `{"style": "dashcore"}`. It holds no tokens. Changing the internal style is one edit here and one design-kit release.

### 2. Structure in code, style in variables

- **Structure** ships as package code, the same in every app: the two shells, page header, flash, account footer, empty state, status tag, and table treatment. These are Blade components that work with or without Flux, because 22 of the 24 apps don't use Flux.
- **Style** is CSS custom properties only, generated by `Resolver` from the seven decisions. Screens use role tokens and never a hex, a font name, or a Tailwind grey.

design-kit ships the `dashcore` style as a built CSS file in the package. An app imports it from `vendor/`, the way `dashcore/ui` works today:

```css
@import 'tailwindcss';
@import '../../vendor/dashcore/design-kit/dist/dashcore.css';
@source '../../vendor/dashcore/design-kit/resources/views';
```

The contrast check runs when design-kit is built, not when it's applied. A style that fails contrast can't be released.

### 3. Updates travel as a copied release

design-kit stays private (decided 17 October 2026), and a private package can't be downloaded by CI or a Laravel Cloud build. So every app carries the release it runs in `packages/dashcore/design-kit`, the way it carries `dashcore/bridge`. `packages/design-kit/bin/vendor-into <app>` copies a `design-kit/vX.Y.Z` tag in. A style or rule change is a tag, then one PR per app that copies it in. Herd Companion already rolls bridge releases across the fleet this way (`FleetBridgeService`), and design-kit can join it.

There's no runtime fetch from this site. An app must render the same whether design.dashcore.com is up or not.

### 4. Enforcement is a ratchet

`design:audit` already exists and reports counts by rule. Two changes make it enforcement:

- **It runs in every app's CI** (with `--report`), so `/fleet` shows the whole fleet rather than the apps that opted in.
- **It ratchets.** An app's findings on the day it joins are recorded as its allowance, the same way `dashcore/testkit` handles route guards. A build fails only when a count goes up. The allowance only shrinks, and `/fleet` shows each app's allowance falling over time.

A new audit rule arrives with its own allowance at today's count, so a release never turns a working build red. This matches the existing rule that a tightening ships with its audit check.

## Decided

Agreed 16 October 2026.

- **A. The `dashcore` style is today's look.** Fraunces and Inter, warm, the ink accent, sharp corners. The standard is extended to express it rather than the look being changed to fit the standard.
- **B. `dc-*` token names stay as aliases** of the role tokens for one major version, so the eight `dashcore/ui` apps move without touching a view. The audit reports `dc-*` use from the following major onward.
- **C. Both component prefixes work for one major version,** `<x-ds::…>` and `<x-dashcore::…>`. After that only `<x-ds::…>` stays.

Anything the `dashcore` style needs that a client design must not have sits below the `prompt-end` marker. The generator reads every section above its marker (`Standard::prompt()` takes every file but `00`, not only `01`–`09`), so that is the only place a client design can't pick it up from.

## Where the two standards conflict

Keeping today's look means more than a pairing and an accent. `DESIGN.md` also differs from the standard's **fixed** layer, the part that is supposed to be the same in every app. Each row needs one answer before Phase 0 can finish.

| # | Rule | `DESIGN.md` | `standard/` | Layer |
|---|---|---|---|---|
| 1 | Fonts | Fraunces and Inter | Five pairings. Inter is excluded by name as the starter default, and a Fraunces pairing was retired on 11 September. | Decision |
| 2 | Accent | `#4a4438`, near-ink | Saturation 45–85 | Decision |
| 3 | Neutrals | Its own warm set: `#f5f2ec` page, white surface | Tailwind stone for `warm`: white page | Decision |
| 4 | Type scale | Title 28/500, section 20/500, label 11px uppercase, table 13px | Title 24/600, section 18/600, nothing under 12px ever, table 14px | Fixed |
| 5 | Status colours | Muted olive, ochre, brick | Green, amber, red, blue at 700, "never change per project" | Fixed |
| 6 | Table rows | 44px | 48 comfortable, 40 compact | Fixed |
| 7 | Radius | 4px ceiling on everything, `rounded-full` clamped too | Sharp: 2–8px, `rounded-full` unaffected | Decision, plus a clamp |
| 8 | Destructive action | Outline in danger, never a fill | Danger fill, white text | Fixed |
| 9 | Selected tab or in-page nav | Ink, not accent | Accent | Fixed |
| 10 | Sidebar | 15rem, surface | 16rem, sunken in light | Fixed |
| 11 | Status tag | 2px left border on the tint, not a pill | `x-ds::badge` soft fill | Fixed |
| 12 | Code blocks, charts | Rules for both | Code: none. Charts: "no rule yet" | Missing here |

Rows 1–3 and 7 fit decision A: they are the style's own values, kept internal-only below the marker.

Rows 4–6 and 8–11 are the real question. "Structure is shared, identity is not" is principle 3; an internal-only structure is a third kind of app, and breaks it. Each row goes one of two ways: **the standard wins**, and the eight `dashcore/ui` apps shift a little when they move; or **`DESIGN.md` wins**, and the standard changes for every app, client designs included, with a changelog entry and an audit rule if it tightens.

Row 12 is additive. `DESIGN.md`'s rules come into the standard as written.

**Answered 16 October 2026:**

- **The standard wins** on 4 (type scale), 5 (status colours) and 10 (sidebar).
- **`DESIGN.md` wins, for every app,** on 6 (44px rows), 8 (destructive as an outline), 9 (selected tab in ink) and 11 (badge as a tag with a leading rule). None of the four needs a screen edited: the adapter's CSS, `Resolver` and `x-ds::badge` carry them.
- **Rows 1–3 and 7** are section 14's four exceptions, below the marker.
- **Row 12** is in 06.

Measuring the style moved two values: the light page to `#f7f4ef`, because success and warning text measured 4.49:1 on `#f5f2ec`, and, in dark, a lighter muted step for quiet surfaces at `#aaa397`, because the old one measured 4.35:1 on the accent tint. Figures are in section 14.

## Phases

Each phase ends in a state that holds up if we stop there.

### Phase 0 — settle the standard
- Answer each row of the conflict table, once.
- Write the `dashcore` style into the standard, its internal-only values below the marker, with a changelog entry.
- Move the rest of what `DESIGN.md` says into the standard's own sections, so nothing is left only there.
- The ratchet and the `{"style": …}` form of `design.json` go into `09` with Phase 1, the day the code that does them ships. The standard never describes a mechanism that doesn't exist yet.

**Done when:** `standard/` describes the internal look completely, and `DESIGN.md` has nothing left in it that the standard doesn't say.

### Phase 1 — design-kit carries a style from `vendor/`
- Built-in styles in design-kit, with `dashcore` first and its CSS built from `Resolver`.
- The shell and frame components from `dashcore/ui` move into design-kit, without a Flux dependency, using the `dc-*` aliases and both component prefixes.
- `design:apply` learns `--style=dashcore`. It writes the `@import` and `@source` lines, not a copy of the tokens.
- `design:audit` learns the ratchet: an allowance file, plus a non-zero exit only when a count rises.
- Pilot on **finance**, which uses both Flux and `dashcore/ui`, and **design.dashcore.com** itself.

**Done when:** both pilots render from `vendor/`, and a test release of the style changes both of them with nothing but a dependency PR.

### Phase 2 — every app reports
- Install design-kit and its CI step in all 24 apps, with the audit in report-only mode.
- No screen changes. This phase measures and doesn't fix anything.

**Done when:** `/fleet` lists all 24 apps and we know the real size of the work, app by app.

### Phase 3 — move the `dashcore/ui` apps
- Move api, brain, email, hr, login, sales and security off `dashcore/ui` and onto design-kit. The aliases make this a dependency swap and three CSS lines.
- Archive `dashcoretech/ui` when nothing requires it.

**Done when:** no `composer.json` in the fleet names `dashcore/ui`.

### Phase 4 — migrate the rest, one app at a time
- Run the 16 apps on no shared look as jobs through work.dashcore.com, one commit per screen, using the existing handoff prompt.
- Order by who sees the app and how far off it is: ceo first (it's the origin of the look and the owner's daily screen), then the apps people outside engineering open.
- The 5 Blade-only apps need the shell and role tokens, not Flux. website is the public site and follows 13 (public pages), not the shell.

**Done when:** every app's allowance is zero or covered by a reasoned `@ds-audit-ignore`.

### Phase 5 — the ratchet is on everywhere
- The audit fails builds fleet-wide when a count rises.
- From here, a change to the internal style is: edit here, release design-kit, merge the dependency PRs.

## What this changes in this repository

- **`PURPOSE.md`:** remove "Not the fleet's shared shell". This app is now the fleet's shared look, and the `dashcore/ui` paragraph becomes history.
- **`packages/design-kit`:** gains styles, the frame components, the `vendor/` CSS build, and the ratchet. Each is a major release with an "Upgrading to" section, as now.
- **`/fleet`:** shows each app's allowance and its trend, not only its findings.
- **`app/Design/`:** `Resolver` and `Css` run at package build time as well as here, so the shipped CSS and the pages here can't disagree.

## Risks

- **16 migrations is the real cost.** Phases 0–3 are weeks; phase 4 is most of the effort. The ratchet means it can go at any pace without anything going red.
- **A bad style release reaches every app.** The contrast check gates the build. The style also ships as a minor release, so a dependency PR shows the change before merge, and `/fleet` reports which version each app is on.
- **Flux and the shell overlap.** `dashcore/ui`'s README already lists the places they clash (`flux:main`, the accent, the appearance class). Those notes move into design-kit's README with the components.
